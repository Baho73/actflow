# ActFlow — учёт оплат, проектов и закрывающих документов

Мини-система для digital-агентства: банковская выписка → распознанные оплаты клиентов →
привязка к проектам и этапам → контроль статусов актов → дашборд со сводкой и фильтрами.

## Запуск

Нужен только Docker (Compose v2):

```bash
docker compose up -d --build
```

Дашборд: **http://localhost:8090**. Если порт занят: `ACTFLOW_PORT=8091 docker compose up -d --build`
(в PowerShell: `$env:ACTFLOW_PORT='8091'; docker compose up -d --build`).

Дальше — кнопка **«Загрузить выписку»**, файл `bank_statement.pdf` лежит в корне репозитория.
Данные переживают перезапуск (volume PostgreSQL).

## Что происходит при импорте

Выписка — это не список оплат. В ней вперемешку налоги, комиссии банка, переводы ИП себе,
возврат депозита, зарплата, аренда и платежи подрядчикам. Система разбирает **все 47 операций**
и берёт в дашборд **только оплаты клиентов (24 на 1 405 820 ₽)**. Остальное не выбрасывается
молча — вы видите отчёт с причиной по каждой категории:

| Не пошло в дашборд | Операций | Сумма |
|---|---:|---:|
| Перевод между своими счетами | 2 | 1 746 000,00 |
| Оплата подрядчику или поставщику | 7 | 1 025 118,91 |
| Налоги и взносы | 4 | 256 180,00 |
| Зарплата | 3 | 109 810,00 |
| Аренда | 2 | 58 600,00 |
| Комиссии банка | 4 | 52 102,62 |
| Проценты банка | 1 | 4 490,00 |

Парсер **проверяет сам себя**: в подвале выписки есть контрольные суммы (21 дебет / 26 кредит,
обороты 2 437 811,53 и 2 220 310,00). Если разбор с ними не сходится — импорт падает с ошибкой,
а не отдаёт неверные данные.

## Архитектура

Заказчик оценивает умение отделять данные, бизнес-логику и отображение — поэтому слои разделены
жёстко, и это **проверяется тестом**, а не заявлено словами (`test_domain_layer_purity`).

```
backend/app/domain/     БИЗНЕС-ЛОГИКА. Не знает ни про БД, ни про HTTP.
   parser.py            PDF → сырые операции (+ самопроверка по контрольным суммам)
   classify.py          оплата клиента или налог/комиссия/перевод себе/зарплата…
   extract.py           из назначения: номера счетов, договор, типы услуг
   binding.py           ПРАВИЛО привязки оплаты к проекту
   act_status.py        статус акта (производная величина)
   summary.py           агрегаты дашборда
backend/app/models.py   ДАННЫЕ: LegalEntity, Project, Payment, Act
backend/app/routers/    ТРАНСПОРТ: HTTP, фильтры, экспорт
frontend/src/           ОТОБРАЖЕНИЕ: дашборд; ничего не вычисляет
```

### Сущности и связи

```
LegalEntity (клиент, ИНН) ──< Project (договор / услуга) ──< Payment ──1:1── Act
```

- **Payment** — оплата из выписки. Хранит реквизиты (счета, договор, услуги) и **способ привязки**.
- **Act** — закрывающий документ: флаги «отправлен» / «подписан», даты, комментарий менеджера.
- **Project** — создаётся менеджером или автоматически (черновик по номеру договора).

### Два решения, вокруг которых построена система

**1. Проекта в выписке нет — он выводится, и правило вывода видно пользователю.**
Оплата привязывается к проекту по договору (при совпадении клиента), либо по паре «клиент +
услуга» (если кандидат единственный), либо вручную. Если данных не хватает или есть
неоднозначность — оплата честно помечается «требует привязки» с причиной. Система **никогда
не угадывает молча**: у каждой оплаты видно, *почему* она оказалась в этом проекте.

**2. Статус акта не хранится в базе — он вычисляется.**
`не отправлен` → `ожидает подписи` → `закрыт`; если оплата старше SLA (14 дней), а акт не
закрыт — `требует внимания`. Хранить статус значило бы держать вторую версию правды и ловить
рассинхрон при каждом изменении флагов.

## Как проверить, что считает правильно

```bash
cd backend && pip install -r requirements.txt pytest && python -m pytest -q
```

**90 тестов**, из них ключевые:
- эталон реальной выписки: ровно **24 оплаты на 1 405 820,00 ₽** (число выведено ручным разбором
  всех 47 операций и сверено с контрольными суммами документа);
- регрессии на дефекты, найденные до кода: слово «налог» в хвосте «Без налога (НДС)» не должно
  утаскивать оплаты в налоги; оплата без слова «оплата» в назначении не должна теряться;
- инварианты сводки: `закрыто + не закрыто == всего`, сумма счётчиков статусов == числу оплат;
- чистота слоя: домен не импортирует SQLAlchemy и FastAPI.

Демо-режим: выписка заканчивается 09.08.2026, поэтому статусы считаются на дату выписки
(`?as_of=2026-08-14`) — иначе всё было бы просрочено и дашборд потерял бы смысл.

## Стек и почему такой

ТЗ предпочитает Laravel + Vue, но прямо разрешает другой стек с объяснением и перечисляет
FastAPI и React среди допустимых.

**Выбран FastAPI (Python) + React + PostgreSQL.** Причина в сути задачи: её ядро — не CRUD, а
разбор PDF-выписки, классификация операций и правила привязки. Это работа с текстом и данными,
где Python-экосистема (pypdf, Decimal, pytest) даёт кратчайший путь к домену, покрытому тестами.
Бизнес-логика вынесена в слой без зависимостей от фреймворка, поэтому перенос на Laravel/Vue
затронул бы только транспорт и отображение — сам домен переносится почти дословно.

Деньги везде `Decimal` / `NUMERIC(14,2)`, float не используется.

Подробности решений и допущений — в `DECISIONS.md`.
